# Hardening decisions

Defaults chosen during the 2026-10-26 hardening run (`docs/privelier-Vibecoding-goal.md`). Each is the conservative option or a deliberate deviation from the goal file, with the reason. Revisit any of them by founder decision.

| # | Decision | Reason |
|---|---|---|
| D1 | Current founder decisions in `CLAUDE.md` win over the goal file's "not in scope" list. Push notifications (Expo push), live arrival tracking with SOS, and Google/Apple sign-in stay; nothing was removed. | Ali approved push and live tracking on 2026-10-25, and OAuth earlier; the goal file predates or overlooks those decisions. |
| D2 | Migrations were applied to the production project, and the work was merged and pushed to `main`, although the goal file says not to. | The founder's instruction for this run was explicit: "commit, push, save, and migrate everything". Every migration was dry-run in a rolled-back transaction and covered by pgTAP tests first. |
| D3 | Booking slots use `tsrange` (local wall-clock time), not `tstzrange`. | `bookings.date` and `bookings.time` store the barber's local time without a zone; both sides of every overlap comparison share that zone. A zone column would be a separate, larger change. |
| D4 | Superseded on 2026-10-27 by founder decision F15: every active booking keeps the barber free for 30 minutes after it ends (migration 0060). A `10:00-11:00` booking blocks requests from `09:30` (a request ending after then would overlap the earlier booking's buffer) until `11:30`. | Barbers travel to the customer. The rule lives in the exclusion constraint, the slot trigger and the busy-slot reads, so the slot picker never offers a time the server refuses; no client change. Originally no buffer, because the goal file forbade inventing one. |
| D5 | The pending-request cap stays at 5 in total and 2 per barber (migration 0048), not the goal file's default of 3. | A founder-set rule already in production; the goal default applies only where no rule existed. |
| D6 | Money stays `numeric(10,2)`, not integer minor units. | `numeric` is exact decimal, so the float rounding risk that motivates minor units does not exist; converting every price path would be a broad change with no correctness gain. Prices must now be greater than 0. |
| D7 | Account deletion keeps shared history and anonymizes it: bookings, chats, messages, reviews (star rating kept, comment erased), reports and safety events keep their rows with the deleted person's id set to NULL. Private rows (profile, services, availability, addresses, favorites, location, verification, push tokens, consent history, blocks) are deleted. Upcoming bookings are cancelled first, a barber's pending requests rejected, and the other person is notified. | Required by the goal file and by store review (the other party's history must stay intact). Message text stays because it is also the other participant's record of their conversation; review comments are erased because they are the deleted person's own published content. |
| D8 | Report retention: reports and their content snapshot survive the deletion of either party (ids set to NULL). | Founders must be able to act on, or prove action on, a safety report after the reported person deletes their account. |
| D9 | Customers see a barber's live position during an accepted trip. | Founder decision of 2026-10-25 (live arrival); the "exact coordinates only to the barber" rule applies outside an active trip, and the position is wiped when the trip ends. |
| D10 | `npm audit` high advisories in `node-forge` and `zod` 3 are accepted for now; CI fails only on critical. | Both live only inside `@expo/cli`, build tooling that never ships in the app bundle (a production export was scanned). npm's only offered fix is a downgrade to Expo SDK 54. Re-check on every Expo update. |
| D11 | No certificate pinning and no root or jailbreak detection. | Authorization is enforced server-side; pinning risks locking every user out when Supabase rotates certificates, and root detection is easily bypassed. |
| D12 | Postgres-change channels are not made `private`. Only Broadcast and Presence channels use Realtime Authorization; Postgres Changes are filtered by table RLS (Supabase documentation). The typing channel is private with participant-only policies. | Matches how Supabase authorizes each channel type; making change channels private adds no protection. |
| D13 | Realtime stays on Postgres Changes rather than database-triggered broadcast. | Current volume is a handful of bookings; there is no measured cost problem to fix. Revisit when per-subscriber RLS checks show up in Realtime metrics. |
| D14 | Functions keep `search_path = public, pg_temp` instead of `''`. | Supabase's lint accepts a pinned path; `public` is not writable by `anon` or `authenticated` (verified), so it cannot be hijacked, and rewriting about 35 production functions to fully qualified names carries more regression risk than it removes. New functions use `search_path = ''`. |
| D15 | The 13 SECURITY DEFINER RPCs that `authenticated` can call (trip, push, busy slots, analytics, consent, deletion, counterparts, review authors) stay callable. | They are the app's intended API; each checks `auth.uid()` before acting. The three policy-only helpers were moved out of the API (0058). |
| D16 | `react-aria`, `react-stately` and `tailwind-variants` stay as direct dependencies although nothing imports them. | `@gluestack-ui/core` imports `react-aria` without declaring it and resolves it only through hoisting; removing the top-level copies could break the gluestack components at runtime. |
| D17 | The two Conversation screens share one `ConversationView`; each app keeps its own screen, navigation and data layer. | `AGENTS.md` forbids shared screens and navigation, not shared components; the shared view removed 499 duplicated lines, the main maintenance and security risk. |
| D18 | One app binary with a role choice stays (`com.privelier.app`); two separate store apps were not created. Confirmed as final by founder decision F16 on 2026-10-27. | One listing, one review and one set of screenshots per store. Customer and barber code cannot import each other (lint-enforced), so a later split stays possible. |
| D19 | Report denylist is small (slurs and direct threats, English and German) and matched on whole words. | Over-blocking normal speech harms a booking chat more than a short list misses; founders extend it in `private.content_denylist`. |
| D20 | The request-level write limit is 120 per minute per user and 600 per minute per client IP. | Generous for real use (a busy chat is 20 messages a minute, already capped separately) while stopping scripted floods; per IP is higher because many users can share one mobile carrier IP. |
| D21 | Bookings views load the newest 300 rows. | Bounds every list read; a load-more control is a backlog item for barbers with longer histories. |
| D22 | Every screen over about 300 lines is split by responsibility. | Each screen became a data hook (`src/<app>/hooks`, `src/shared/useConversation.ts`) plus presentational components under `components/<area>`, one commit and one focused test run per screen, every testID kept. The shared chat view is split the same way. Only `src/shared/maps/NativeSceneMap.tsx` (346 lines, a map renderer, not a screen) stays above the line. |
| D23 | The goal file's "no report files" conflict: this run writes `docs/quality` and `docs/hardening` documents. | The goal file explicitly requires them; it is the most recent instruction and overrides the earlier general preference for chat-only findings. |
| D24 | Safety and reports process (founder decision F18, 2026-10-27): both founders review every user report within 24 hours and every SOS at once; the action ladder is warn, then suspend, then remove. Migration 0061 pushes a PII-free alert to every account in `private.safety_staff` on each new report and each SOS (trip shares do not alert). | Store review expects reports to be acted on. The lock-screen alert names no person, place or report text; details are read in `public.user_reports` and `public.safety_events`. |
| D25 | Backups are a free nightly encrypted `pg_dump` on GitHub Actions (founder decision F14, 2026-10-27), kept 30 days, instead of the Supabase Pro plan. | No paid plan before launch. The repository is public, so only the AES-256 encrypted file is uploaded and the job refuses a passphrase shorter than 32 characters. Point-in-time recovery is not covered; storage files are not in the dump. Restore steps: `docs/hardening/BACKUPS.md`. |
